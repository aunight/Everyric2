# 平假名發音標記設計

## Problem 1-Pager

### 背景（Background）

Chrome 插件目前把第三種發音標記稱為「假名」，但後端會把日文讀音刻意轉成片假名，
PiP 採點按鈕也顯示「カナ」。因此即使日文原文含有漢字，歌詞與採點畫面附加的讀音仍是
片假名，不符合使用者要求的平假名標註。

### 問題（Problem）

只改設定選項文字會留下三個不一致：

1. 新同步資料的 `pron.kana` 與 `pron_segs.kana` 仍是片假名。
2. 已經快取在 Chrome 的舊資料仍會顯示片假名。
3. 一般歌詞與採點音符經過不同渲染路徑，若只修其中一處，另一處仍會錯。

### 目標（Goal）

- 日文原文完整保留漢字與假名，不替換歌詞本文。
- 原文含漢字時，使用日 K 常見的振假名排版，把平假名直接標在對應漢字上方。
- 採點音符保留原文字詞，並把對應平假名標在漢字上方。
- 新產生的所有 `kana` 發音值與分段文字使用平假名。
- 舊快取若含片假名，Chrome 顯示前自動正規化為平假名。
- 設定與採點按鈕明確標示「平假名」。

### 非目標（Non-goals）

- 不把歌詞原文中的漢字或片假名改寫成平假名。
- 不變更音高、採點、逐字時間或莫拉分段演算法。
- 不重新命名既有 API/儲存欄位 `kana`。
- 沒有可靠逐字時間時不猜測漢字與讀音對位，保留既有獨立發音列作為安全退路。

### 約束（Constraints）

- `kana` 欄位與 `pronunciationScript: "kana"` 必須保留，確保舊版插件、快取與資料庫相容。
- 顯示字串與 `pron_segs.kana` 重建出的字串必須完全一致。
- 中文歌曲仍固定顯示中文原文與拼音，不套用日文讀音規則。

## 採用方案

採用「後端源頭修正 + 前端相容正規化」：

1. 後端保留 `kana` 鍵，但所有日文、韓文與拉丁轉寫結果在寫入前統一轉成平假名。
2. Chrome 的共用發音解析器在讀取 `kana` 字串與分段時，再做一次片假名轉平假名，
   讓舊快取立即得到正確顯示。
3. 一般歌詞、採點底部發音與採點音符標籤全部繼續呼叫共用解析器，不新增分岔。
4. 四種介面語言的選項名稱改成「平假名 / Hiragana / ひらがな / 히라가나」；
   PiP 短按鈕顯示「ひら」。
5. Chrome 以原文字詞時間和讀音莫拉時間的最大重疊做對位，只在含漢字的字詞上建立
   `<ruby><rt>`；已有振假名時不再重複顯示整行讀音。
6. 採點畫布沿用同一組音符 `lyric`/`pron` 對位，把小型平假名畫在漢字正上方。

## 替代方案

### 只改前端

能立即修正畫面，但 API 與新快取仍保存片假名，其他客戶端仍會錯，因此不採用。

### 把 `kana` 全面改名為 `hiragana`

語意最清楚，但會破壞現有設定、快取和伺服器契約，遷移成本與風險不成比例，因此不採用。

## 驗收條件

- `僕は歌う` 的原文仍為 `僕は歌う`，`僕` 上方顯示 `ぼく`，假名原文不重複標註。
- 舊資料 `ボク ワ ウタウ` 經一般歌詞和採點路徑顯示為 `ぼく わ うたう`。
- 採點音符上的 `lyric` 保留漢字，`pron` 使用平假名。
- 一般歌詞與 PiP 當前歌詞以 ruby 顯示，採點畫布先畫上方平假名、再畫下方漢字。
- `pron.kana` 與 `pron_segs.kana` 均不含一般片假名字元。
- 設定選項與 PiP 控制不再出現「假名」或「カナ」作為模式名稱。
