# 繁體歌詞與採點括號過濾設計

## Problem 1-Pager

### 背景（Background）

Chrome 擴充功能已在網易雲即時抓取路徑把中文原文與翻譯轉為繁體，但轉換發生在
`FETCH_NETEASE`／`PICK_NETEASE` 的背景處理階段。從網易雲建立並保存到 Everyric
伺服器的舊同步資料，重新查詢時會以 `Everyric` 來源直接進入畫面，不再經過網易雲轉換。

採點視窗則由 PiP 的 `collectPitchData()` 直接讀取完整 `LyricLine[]`，所以括號內的
和聲、口號或重複襯詞也會建立採點歌詞標籤。

### 問題（Problem）

1. 中文歌詞是否顯示繁體取決於資料來源和快取狀態；Everyric 舊快取仍可能顯示簡體。
2. 採點視窗會顯示使用者明確不需要的括號內容，例如
   `(We don't we don't we don't)`。

### 目標（Goal）

- 所有來源的中文歌詞在進入 Chrome 畫面前統一顯示為繁體。
- 日文原文的漢字字形不因中文轉換而改變。
- 採點視窗移除 `(...)`、`（...）`、`[...]`、`【...】` 片段。
- 括號移除後整行為空時，不建立該行的可見採點歌詞、音符文字或逐字文字。
- 一般歌詞面板仍保留括號內容。

### 非目標（Non-goals）

- 不回寫或批次修改 Everyric 伺服器既有資料。
- 不從一般歌詞面板刪除括號內容。
- 不處理巢狀或跨行括號；以單行、非巢狀片段為支援範圍。
- 不在本次修復中修改 RMVPE、FCPE、Demucs、Dereverb、GAME 或 MuScriptor。

### 約束（Constraints）

- 轉換必須在所有歌詞來源共用的入口執行，不能再依賴來源分支。
- 日文原文、發音時間、音符時間、翻譯索引與來源標註必須保留。
- 採點過濾必須使用衍生資料，不能改動 `currentData.lines`。
- Chrome 正式建置與既有測試必須保持通過。

## 方案比較

### 方案 A：只在網易雲與 Everyric 兩條來源分支補轉換

改動小，但其他來源或未來新增來源仍可能漏掉；同一規則會散落在多個資料邊界。

### 方案 B：在 `applyLyricsData()` 共用入口正規化，採點另建純過濾器

所有資料在存入 `currentData` 前走同一個繁體正規化函式；PiP 在建立採點資料前，
使用不改動原陣列的純函式移除括號片段。這是採用方案，涵蓋舊快取且不影響一般歌詞。

### 方案 C：伺服器資料庫批次轉換

能永久清理舊資料，但有不可逆資料變更、日文漢字誤轉與部署協調風險；不適合這次
Chrome 顯示修復。

## 架構

### 共用繁體正規化

新增純模組 `src/lib/traditional-lyrics.ts`：

- 以整份原文語料偵測語言。
- 原文語料為中文時，轉換 `line.text`、`line.words[].word` 與重新組成的 `plainText`。
- `translationLang === "zh"` 時轉換行內翻譯。
- `translationsByLang.zh` 一律轉換，並保持陣列長度及索引。
- 回傳新的 `LyricsData` 與行／逐字物件，不修改傳入資料。

`netease-lyrics.ts` 也使用同一個字串轉換器，避免出現兩套不同 OpenCC 規則。
`applyLyricsData()` 在移除製作人員後、指定 `currentData` 前呼叫共用正規化，因此
Everyric 快取、LRCLIB、網易雲、字幕與手動歌詞採用相同顯示邊界。

### 採點專用括號過濾

新增純函式，逐行移除下列單行非巢狀片段：

- 半形圓括號：`(...)`
- 全形圓括號：`（...）`
- 半形方括號：`[...]`
- 全形方括號：`【...】`

函式同步處理 `line.text` 與 `line.words`：

- 先從 `line.text` 建立括號字元遮罩，再依原始文字順序把 `line.words[].word`
  對回遮罩；位於括號內的字元不進入採點衍生資料，跨多個逐字項目的括號仍能正確移除。
- 行內剩餘文字會正規化多餘空白。
- 清空的行保留同索引的空白占位資料再傳給 `collectPitchData()`，讓播放引擎的原始行索引
  與 PiP 採點索引維持 1:1；占位資料不含逐字與音符，所以畫面上不可見也不參與評分。
- 原始 `LyricLine[]` 保持不變，普通歌詞面板仍顯示括號內容。

括號片段對應的音符不建立歌詞標籤；整行只有括號時，PiP 只保留不可見的索引占位。
`PipController.setLines()` 保存同長度的採點衍生副本，因此換行高亮、上一句／下一句與
點擊跳轉不會因刪除陣列元素而錯位；YouTube 頁面的普通歌詞面板仍使用原始資料。

## 資料流程

```text
任何歌詞來源
  → stripProductionCredits
  → normalizeTraditionalLyricsData
  → currentData / 一般歌詞畫面
  → scoringLines（衍生副本，移除括號）
  → collectPitchData / 採點視窗
```

## 錯誤處理

- 空資料與未知語言原樣通過。
- 括號不成對時不刪除，避免誤吃正常歌詞。
- 括號過濾後沒有可採點行時，沿用既有「無音符」狀態，不拋出例外。
- OpenCC 轉換為同步且冪等；重複載入同一份快取不會持續改變文字。

## 測試

- Everyric 來源的簡體中文原文、逐字文字與 `plainText` 轉為繁體。
- 日文原文維持不變，中文翻譯層仍轉為繁體。
- 所有來源在 `applyLyricsData()` 指定 `currentData` 前經過共用正規化。
- 採點過濾移除四種括號片段。
- 混合文字只留下括號外內容；括號整行被略過。
- 不成對括號保留。
- 原始歌詞物件與一般歌詞內容未被修改。
- 跑完整 Chrome 測試、TypeScript 型別檢查、採點規則檢查與正式建置。
