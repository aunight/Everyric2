# 日 K 式採點麥克風軌跡設計

## Problem 1-Pager

### 背景（Background）

Everyric 的 Document PiP 音高軌已能取得麥克風音高、與旋律音符比對並計算分數。
目前麥克風輸入只畫成每 45ms 一顆小圓點；在密集格線、音符與文字之間不夠醒目，
使用者難以快速確認自己實際唱出的音高。使用者希望改成日本卡拉 OK 常見的橫線軌跡，
同時保留切回點狀顯示的能力。

### 問題（Problem）

1. 點狀軌跡太小且彼此分離，無法清楚呈現持續音與音準偏差。
2. 採點與麥克風是兩個獨立開關；只開採點時沒有輸入，操作不像「開一次就能唱」。
3. `getMicSamples()` 在麥克風未運作時仍可能回傳空陣列，採點器會持續推進並把未唱音符
   納入 0 分，HUD 也無法正確顯示「麥克風關閉」。

### 目標（Goal）

- 麥克風音高預設以清楚的粗橫線／短折線疊在目標音符軌上。
- 連續樣本才接線；換氣、偵測中斷或不合理的大跳音必須斷線。
- 採點狀態下沿用命中綠、接近黃、失誤紅；未採點時使用青色。
- PiP 內提供「線／點」即時切換並記住設定。
- 開啟採點時自動開啟麥克風音高，不需要再找第二個開關。
- 麥克風未啟動或權限失敗時顯示明確狀態，且不累積假 0 分。
- 現有分數歷史、最高分、中文歌詞與發音切換行為不得回歸。

### 非目標（Non-goals）

- 不更換目前的 ACF 麥克風音高偵測器。
- 不調整命中／接近／失誤的半音門檻與總分公式。
- 不新增排行榜、雲端分數或完整 DAM 表現力／顫音評分。
- 不修改伺服器旋律抽取與歌詞時間軸。

### 約束（Constraints）

- 繪製仍使用現有 PiP Canvas，不引入新的視覺化依賴。
- 保留既有點狀模式，讓低效能裝置或偏好舊畫面的使用者可切回。
- 設定必須經既有 `Settings`／`saveSettings` 流程持久化。
- 所有新判定邏輯應抽成可直接由 Node 測試的純函式。
- 不覆蓋目前工作樹中其他未提交的歌詞、語言與 UI 修改。

## 方案比較

### A. 分段粗線軌跡（採用）

把相鄰麥克風樣本依時間接成短線，時間間隔過大或音高跳動過大就另起一段。線條使用圓角、
深色外框與判定色內線，兼顧暗色／亮色背景。它最接近日 K 的視覺語言，也能保留實際唱高
或唱低的形狀。

### B. 單一連續折線

實作最少、畫面最強，但會跨過換氣與短暫偵測失敗，把不連續聲音畫成錯誤滑音。

### C. 直接填色目標音符

命中狀態非常直觀，但看不到使用者實際音高落在哪裡，也不符合「顯示麥克風偵測結果」。

## 元件與資料流

1. `MicPitch` 維持每 45ms 產生 `{ at, midi }`。
2. `PipController.renderPitch()` 將牆鐘樣本換算成歌曲時間、套用八度校正並取得採點判定。
3. 新的純函式接收已換算的軌跡點，只在下列條件成立時產生線段：
   - 相鄰點時間差不超過 160ms。
   - 相鄰音高差不超過 4 個半音。
4. `line` 模式先畫低透明度外框，再畫 5px 判定色圓角線；最新端點加小圓頭。
5. `dots` 模式沿用現有圓點繪製。
6. PiP 的模式按鈕呼叫 `onMicDisplayModeChange`，由 content script 經 `saveSettings`
   保存並回推 `setMicDisplayMode()`。

## 狀態與錯誤處理

- `getMicSamples` 改為回傳 `MicSample[] | null`：`null` 表示麥克風沒有運作，空陣列表示
  已運作但目前沒有可靠音高。
- 只有非 `null` 時才呼叫 `ScoreTracker.advance()`；因此權限失敗不會造成假 0 分。
- 開啟 `karaokeScoring` 時，content script 同一筆設定更新會強制 `micPitch: true`。
- 權限被拒絕時沿用既有 HUD「採點 — 麥克風關閉」，不拋出例外。
- 切換線／點只影響繪製，不重設採點器或目前分數。

## 測試與驗收

- 純函式測試連續樣本會接線、時間斷點與大幅跳音會斷線。
- 設定測試確認預設為 `line`，型別與 PiP 回呼完整接線。
- 行為測試確認開啟採點會同時開啟麥克風。
- 靜態 UI 測試確認 PiP 有線／點切換按鈕且兩模式使用不同繪製路徑。
- 執行 Chrome 擴充功能完整測試與 production build。
- 實際 PiP 畫面驗收：線條清晰覆蓋目標音符、顏色隨判定切換、斷音不被錯接。
