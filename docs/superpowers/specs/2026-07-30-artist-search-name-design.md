# 顯示藝人與搜尋藝人名稱分離設計

## Problem 1-Pager

### 背景（Background）

YouTube 與 YouTube Music 取得的藝人欄位可能同時包含合作歌手及頻道資訊，例如
`A feat. B`、`A & B`、`A, B` 或 `A - Topic`。目前 Everyric 會把完整字串直接送往
LRCLIB、網易雲及候選搜尋；外部來源的藝人欄位通常只接受主要藝人，因此完整合作名單
容易造成零結果。

合作歌手仍是使用者需要看到的歌曲資訊，不能為了搜尋而從標題列刪除。YouTube 自動建立的
`- Topic` 則只是頻道後綴，不是藝人名稱，不應出現在畫面。

### 問題（Problem）

目前只有一份 `SongInfo.artist` 同時負責畫面顯示、資料保存與外部搜尋，導致兩種需求衝突：

- 保留完整合作歌手可以正確顯示歌曲資訊。
- 外部搜尋需要較短的主要藝人名稱才能提高命中率。
- `mediaSession.metadata.artist` 等路徑未必會移除 `- Topic`，行為不一致。

### 目標（Goal）

- 畫面及歌曲資料保留 `feat.`、`featuring`、`ft.`、`&`、`,`、`，` 後的合作歌手。
- 畫面及歌曲資料只移除結尾的 YouTube `- Topic` 頻道後綴。
- 所有歌詞及候選搜尋只傳送第一位主要藝人。
- 自動偵測與手動輸入的藝人查詢套用相同搜尋規則。
- LRCLIB、網易雲及伺服器候選搜尋共用同一個純函式，不各自維護正規表示式。

### 非目標（Non-goals）

- 不刪除畫面上的合作歌手。
- 不改寫外部搜尋結果回傳的藝人名單。
- 不推測團體成員或把正式團名拆成多位藝人。
- 不修改歌曲標題、歌詞來源排序或候選評分公式。
- 不處理 RMVPE、Demucs、Dereverb 或採點顯示。

### 約束（Constraints）

- 顯示規則與搜尋規則必須是兩個名稱明確的純函式。
- 舊資料及手動輸入可能仍含完整合作名單，因此搜尋邊界必須再次正規化。
- 只有破折號要求前後空白，避免切斷 `A-Teens`；`feat`、`&` 與逗號依使用者要求
  一律視為搜尋分隔符。
- 清理結果若為空字串，搜尋時退回空藝人查詢，不把分隔符後文字誤當主要藝人。
- 現有 Chrome 儲存資料結構及 `SongInfo` 型別維持相容。

## 方案比較

### A. 分離顯示名稱與搜尋名稱（採用）

保留 `SongInfo.artist` 作為顯示及保存值，只移除 `- Topic`。送出外部查詢前另外呼叫
`primaryArtistForSearch()` 取得主要藝人。資料沒有損失，且所有來源使用相同搜尋名。

### B. 偵測時永久只保留主要藝人

實作簡單，但會讓標題列與保存資料失去合作歌手，不符合需求。

### C. 保留完整名稱，搜尋失敗後逐來源重試

能保留資料，但每個來源都需要額外請求與不同重試邏輯，搜尋較慢且仍未處理 Topic 顯示。

## 名稱規則

### 顯示與保存

`artistForDisplay(raw)`：

1. 正規化連續空白並去除首尾空白。
2. 只移除結尾的 ` - Topic`、` – Topic` 或 ` — Topic`，不分大小寫。
3. 保留其他所有合作資訊。

範例：

- `A feat. B` → `A feat. B`
- `A & B` → `A & B`
- `A, B` → `A, B`
- `A - Topic` → `A`
- `A — Official` → `A — Official`

### 外部搜尋

`primaryArtistForSearch(raw)` 先套用顯示清理，再從最早出現的下列分隔符截斷：

- 獨立單字 `feat`、`feat.`、`featuring`、`ft`、`ft.`，不分大小寫。
- 前後可有空白的 `&`。
- 半形逗號 `,` 或全形逗號 `，`。
- 前後有空白的 ` - `、` – `、`、` — ` 頻道或附加資訊分隔。

結果再次正規化空白。分隔符若位於字串開頭，回傳空字串。

範例：

- `A feat. B` → `A`
- `A featuring B` → `A`
- `A ft. B` → `A`
- `A & B` → `A`
- `A, B`、`A，B` → `A`
- `A - Topic`、`A — Official` → `A`
- `A-Teens` → `A-Teens`
- `AC/DC` → `AC/DC`

此規則依使用者要求一律取第一位藝人，因此即使逗號或 `&` 是正式團名的一部分，
搜尋仍只使用其前段；畫面不受影響，仍保留完整正式名稱。

## 元件與資料流

1. 新增單一藝人名稱模組，匯出 `artistForDisplay()` 與
   `primaryArtistForSearch()`。
2. `song-detector.ts` 在每個 metadata、YouTube Music byline、標題解析及頻道名稱路徑
   建立 `SongInfo` 前呼叫 `artistForDisplay()`。
3. `song-title.ts` 可保留解析出的完整合作藝人；最終顯示清理由歌曲偵測層統一處理。
4. LRCLIB、網易雲與背景候選搜尋在建立 URL 或伺服器參數前呼叫
   `primaryArtistForSearch()`。
5. 手動搜尋文字框仍顯示使用者輸入的完整字串，但送出查詢時使用主要藝人名稱。
6. 候選結果顯示來源回傳的完整藝人資訊，不套用搜尋清理。

`SongInfo.artist` 不新增第二個持久化欄位；搜尋名稱是送出請求時才產生的衍生值。

## 錯誤與邊界

- `null`、空白或只有分隔符：顯示及搜尋皆視為沒有藝人。
- `Topic` 不在結尾：不當作頻道後綴移除。
- 名稱內沒有搜尋分隔符：完整保留。
- 手動輸入已是主要藝人：結果不變。
- 舊快取含 `A feat. B`：顯示仍完整，下一次搜尋自動使用 `A`。
- 候選來源回傳多位藝人：列表仍顯示完整資料，方便使用者辨識版本。

## 測試與驗收

先建立失敗測試，涵蓋：

1. 顯示清理只移除結尾 `- Topic`。
2. 顯示清理保留 `feat.`、`&`、逗號及非 Topic 的破折號後綴。
3. 搜尋清理支援 `feat`、`featuring`、`ft`、`&`、半形／全形逗號及有空格破折號。
4. 搜尋清理不切斷 `A-Teens` 或 `AC/DC`。
5. `detectSong()` 的 media session、YouTube Music 及一般 YouTube 路徑都使用顯示清理。
6. LRCLIB、網易雲與手動候選查詢都使用主要藝人搜尋名。
7. 候選結果仍顯示來源回傳的完整合作藝人。

完成後執行 Chrome 擴充功能全量測試、型別檢查、production build 與
`git diff --check`。驗收範例中，頁首顯示 `A feat. B`，實際送往搜尋來源的藝人參數必須是
`A`；頁首若收到 `A - Topic` 則只顯示 `A`。
